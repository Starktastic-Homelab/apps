## Selected approach and boundaries

Use the existing shared PostgreSQL deployment and enrollment/completion gate.
Qualify conversion into the exact stock PostgreSQL schema; do not let a loader
replace tables, types, constraints or indexes. Keep target backend-specific schema
migration records native. Compare every application field, including byte values,
nulls, dates, identities, resource versions/history, password hashes, sessions and
ciphertexts. Refuse silent omission, truncation or a successful loader exit with
errors. Validate the stock schema, sequences and application behavior independently.
No dashboards-only export or replacement installation may discard user state.

PostgreSQL's native SQL timestamps have microsecond precision. A metadata-only
profile found finer fractions in 16 source values across six timestamp columns.
Qualification compares these fields against PostgreSQL's own timestamp cast,
rejects unexpected time/offset changes, and preserves original precision in the
retained source/recovery copy. It does not claim byte-identical SQL timestamp
strings across engines. Binary UTF-8 resource values must round-trip exactly into
native PostgreSQL text; reject malformed bytes rather than replacing them.

Grafana supports PostgreSQL but describes cross-database migration as customer-managed.
The Grafana-owned database-migrator targets MySQL, not this PostgreSQL destination.
Rehearse the existing pinned PGLoader route in disposable copies before deciding
whether it preserves this version's entire application state. If exact preservation
cannot be established, stop for a decision about SQLite on CSI or another method.
Do not silently select a fallback or rewrite migration markers.

Retain a statically bound ext4/RWOP/Retain CSI volume for any necessary private files;
measure current usage and the full dataset growth budget before selecting its size.
Keep the original NFS source admission-held and prune/delete-protected. Use the
existing verified VM retirement/fencing and normal rebuild workflow. Preserve
image, OIDC identity, encryption configuration, renderer identity, datasource
configuration and the existing URLs. Do not move Prometheus/Alertmanager storage.

The Grafana Deployment shares the kube-prometheus-stack Application with other
monitoring components. Scope its Argo hold accordingly, and prove final rendered
changes affect only Grafana and explicitly approved retained storage/gates.
Resolve all overlapping writers, including Filebrowser's parent claim and the NFS
provisioner, before a final cold source copy. Independent alert collection and
notification must not be stopped merely because Grafana is being migrated.

## Acceptance

Require full field/schema conversion proof, an independent dump restore and stock
Grafana startup with its preserved data, permissions, history and encryption state.
Exercise synthetic account/dashboard/datasource data in isolation before real copies.
Prevent real notification delivery from the lab. Production acceptance includes
existing login/session behavior where testable, dashboards/folders, datasource
queries, alert configuration, rendering, OIDC configuration fingerprint, clean Pod
recreation and healthy worker movement with the same retained physical identity.

do not claim it from configuration or token checks alone.

Before production, freeze the exact reviewed commands, identities, backup/restore
and failure boundaries. Record one original outage clock and bounded checkpoints;
never reset a failed phase's clock or replay unknown writes. Before authoritative
target writes, rollback may use the verified unchanged source after full retirement.

stale SQLite. Require a complete current shared PostgreSQL backup, exact-head hosted
checks, inspected diff and merged desired/live equality before owned hold release.
